SQLite＋Chroma/DuckDBで長期記憶を持つAIエージェントを設計する時代

  • 常時稼働型AIで長期記憶が重要になる
  • SQLite＋Chroma/DuckDBの分担が効く
  • 開発者ツールは記憶設計まで問われる

OpenAIの常時稼働型エージェントや各種AI業務ツールの登場で、AIエージェントは「会話するだけ」から「継続的に働く」段階へ移りつつあります。一方で、その進化を支えるには、短期の推論だけでなく、軽量で扱いやすい長期記憶の設計が欠かせません。本稿では、SQLiteを土台にChromaやDuckDBを組み合わせる発想を、最新の開発者ツール/agentフレームワークの動向とあわせて整理します。

As always-on AI agents and AI workflow tools become more common, agent design is shifting from chat to persistent work. This article explains how a lightweight long-term memory stack built around SQLite with Chroma and DuckDB fits into that trend, using only the provided search results as evidence.

OpenAIがDevDay 2026で示した「Dots」は、ユーザーの代わりにタスクをこなす“always-on”なAIエージェントとして紹介されました。[5] さらに、医療事務のような定型業務をAIエージェントで自動化するHeidiのような事例も出てきており、AIは単発の応答を返す道具から、継続的に仕事を進める実行主体へと役割を広げています。[8] こうした流れでは、エージェントが過去の会話や作業文脈をどれだけ正確に保持し、必要な時に引き出せるかが実用性を左右します。[5][8]

このとき有効なのが、記憶を一枚岩にせず役割分担する設計です。SQLiteはアプリのローカル基盤として扱いやすく、メタデータやイベント履歴、ユーザー設定のような“事実の台帳”を保持するのに向いています。そこにChromaのようなベクトル系ストアを重ねれば、会話や文書から抽出した意味的な記憶を検索しやすくなります。さらにDuckDBを加えると、記憶を単なる保存ではなく分析可能なデータとして扱えるため、「いつ」「何が」「どれだけ」起きたかを集計しながらエージェントの行動を改善しやすくなります。AIエージェントが常時稼働する前提では、こうした“保存・検索・分析”の三層構造が設計の中心になります。[5][8]

背景には、AIを組み込む業務ソフトや開発基盤が、単なる生成機能から統合機能へ進化していることがあります。Acumaticaの2026 R2は、AI駆動の自動化、分析、統合を強化し、MCPサポートやネイティブなデータウェアハウスを備えたとされます。[1] これは、エージェントが外部システムや業務データと接続するだけでなく、内部に保持する記憶の構造まで含めて設計する必要があることを示しています。[1] また、Amazon Adsの新しいAIツールや、暗号資産取引の領域でAIエージェント基盤をうたうQuote.Tradeの動きも、業務実装の現場で“エージェント前提”が広がっている証拠です。[2][7]

この文脈でSQLite＋Chroma＋DuckDBの組み合わせが注目されるのは、派手さよりも運用性に価値があるからです。ローカルで完結しやすいSQLiteは、Claude CodeやCursor、GitHub Copilotのような開発者ツールが扱う作業ログや設定との相性がよく、Chromaは会話の意味記憶、DuckDBは長期蓄積された記憶の分析にそれぞれ役割を持てます。重要なのは、エージェントに「すべてを覚えさせる」のではなく、何を台帳化し、何を意味検索に回し、何を分析対象にするかを切り分けることです。記憶を分解して設計することで、常時稼働型のAIでも破綻しにくい構成に近づきます。[5][8]

一方で、こうした記憶層の拡張は、計算基盤とメモリ需要の増大とも無関係ではありません。MicronやSamsungの幹部は、メモリ不足が2028年頃まで続く可能性を示し、2027年のメモリ価格は2026年より高いとの見方も出ています。[3] Micronの好決算と強い見通しも、AI需要がメモリを押し上げている現実を裏づけています。[4][6] つまり、AIエージェントの長期記憶はソフトウェア設計の課題であると同時に、インフラコストの課題でもあります。開発者は、精度だけでなく、保存先の軽量性、検索性能、分析負荷、そして将来のメモリ価格まで見据えてアーキテクチャを選ぶ必要があります。[3][4][6]

結局のところ、長期記憶を持つAIエージェントの設計は、「どのモデルを使うか」だけでは完結しません。常時稼働するエージェントを前提に、SQLiteで事実を、Chromaで意味を、DuckDBで履歴を扱うような分業設計が、開発者ツールやagentフレームワークの次の実装論になりつつあります。[1][5][8]
